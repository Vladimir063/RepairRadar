# RepairRadar: согласованные требования

Дата: 2026-09-21. Источник: запрос пользователя и уточнения в текущем диалоге.

## Результат

Приложение RepairRadar на Java 21, стабильном Spring Boot, Maven и Spring Data JPA. PostgreSQL запускается через Docker Compose. При первом запуске на пустом томе база и таблица адресов создаются без запуска приложения.

Структура таблицы соответствует 13 полям `77/moscow_random_50.csv`, но `Адресная_иерархия` заменяется полным адресом, включая номер дома и дополнительные части номера. Названия столбцов английские. Первичный ключ — `house_guid`, PostgreSQL UUID, значение `Дом_OBJECTGUID`; искусственного идентификатора нет.

Контроллер вызывает отдельный сервис, который читает необходимые XML из `77` и добавляет до 100 случайных новых уникальных адресов. Каждый успешный импорт добавляет до 100 новых адресов, сохраняя существующие строки без изменений. При достаточном количестве новых адресов два вызова дают 100 + 100 = 200. Дубли по house_guid пропускаются; выборка добирается из остальных кандидатов. При ошибке импорта прежние данные сохраняются. Отдельный endpoint удаляет все строки одной операцией. Нужна Postman-коллекция для обоих запросов.

## Принятые проектные решения

- Базовые версии плана: Spring Boot 4.1.1, PostgreSQL 18.6; без SNAPSHOT, milestone, RC, beta и плавающего `latest`. Перед реализацией перепроверить доступность релизов в официальных источниках и Maven Central/Docker registry; более свежий стабильный patch можно зафиксировать с обновлением документации.
- Maven Wrapper, Java release 21, UTF-8; groupId `ru.repairradar`, artifactId `repairradar`.
- Приложение запускается локально через Maven/IDE; Compose запускает только БД. HTTP-порт 8080, PostgreSQL 5432 с возможностью переопределения.
- `POST /api/addresses/import` без тела: синхронный импорт и ответ 200 `{"requested":100,"imported":100,"total":100,"exhausted":false}` после commit. imported — реально добавленные строки, total — размер таблицы в текущей транзакции; exhausted=true, если добавлено меньше 100 из-за исчерпания новых адресов. Остаток 0 также возвращает 200.
- `DELETE /api/addresses` без тела: очистка и ответ 204 после commit; повторная очистка пустой таблицы тоже 204.
- Новая сотня выбирается только среди GUID, которых ещё нет в БД. Дубли пропускаются без изменения старых строк и без ошибки. PostgreSQL INSERT использует ON CONFLICT (house_guid) DO NOTHING; удаление выполняется только отдельным DELETE endpoint.
- При одновременных изменениях одного экземпляра приложения второй запрос получает 409. Выбор новых GUID и запись разных экземпляров сериализуются блокировкой таблицы в PostgreSQL, после полного чтения XML. 409 означает занятую операцию, не наличие дубля.
- XML читаются потоково; CSV служит образцом структуры, Python не участвует в работе приложения.
- Источники: `AS_ADDR_OBJ_2*.XML`, `AS_HOUSES_2*.XML`, `AS_ADM_HIERARCHY_2*.XML`; строго один файл каждого вида одной даты.
- Выбираются актуальные активные дома с номером и активной административной цепочкой региона 77, содержащей улицу уровня 8. `city` равен `Москва`, как в CSV; полная цепочка сохраняет населённые пункты внутри Москвы.
- Существующие XML, CSV и Python-файлы не изменяются. Большие исходные данные не включаются в jar и Git.
- ГАР-справочники типов отсутствуют в рабочей папке. Для известных кодов использовать явно описанные подписи; неизвестный код сохранять в полном адресе буквально с пояснением, не подменять словом «дом» или «корпус».

## Критерии приёмки

1. После `docker compose up -d --wait` существует `public.addresses` с 13 согласованными столбцами и PK `house_guid`, приложение ещё не запускалось.
2. Maven Wrapper собирает проект под Java 21, приложение подключается и проверяет схему.
3. POST по реальным XML при достаточном числе кандидатов добавляет ровно 100 новых уникальных адресов с непустым полным адресом до дома.
4. Повторный POST при достаточном количестве кандидатов увеличивает таблицу со 100 до 200 строк, не изменяя прежние строки. Дубли не вызывают ошибки; при остатке меньше 100 импортируется остаток, при нуле — 0 и HTTP 200. Ошибки чтения/записи сохраняют прежние данные, новые вставки неудачного запроса откатываются.
5. DELETE оставляет ноль строк и выполняется одной массовой операцией через Spring Data.
6. Postman-коллекция импортируется и содержит оба запроса с проверками ответов.
7. Автоматические проверки используют маленькие XML и отдельную PostgreSQL test-базу; данные пользователя не очищаются тестами.
