# RepairRadar

Java 21 · Spring Boot 4.1.1 · Maven 3.9.11 (Wrapper) · PostgreSQL 18.6 · Spring Data JPA.

Приложение читает адреса ГАР из локальных XML и по HTTP добавляет до 1000 случайных **новых** адресов. Повторный вызов увеличивает таблицу: 1000 → 2000 → 3000, пока есть новые кандидаты. Дубли определяются по `house_guid`, пропускаются и не перезаписывают существующие строки.

## Запуск

Нужны JDK 21 и запущенный Docker Desktop с Linux containers. Команды PowerShell из корня проекта:

```powershell
Copy-Item .env.example .env
docker compose up -d --wait
.\mvnw.cmd verify
.\mvnw.cmd spring-boot:run
```

После запуска PostgreSQL таблица `public.addresses` уже создана, даже если Java-приложение ещё не запускалось. Приложение слушает `http://localhost:8080`.

Для сборки и запуска jar:

```powershell
.\mvnw.cmd package
java -Xmx512m -jar target/repairradar-0.0.1-SNAPSHOT.jar
```

На Linux/macOS команды Wrapper: `sh ./mvnw verify` и `sh ./mvnw spring-boot:run`.

Если Maven в Windows выдаёт `PKIX path building failed`, а сертификат доверен операционной системе, можно использовать её хранилище в текущем терминале:

```powershell
$env:MAVEN_OPTS='-Djavax.net.ssl.trustStoreType=Windows-ROOT -Djavax.net.ssl.trustStore=NONE'
.\mvnw.cmd verify
```

Проверка TLS при этом остаётся включённой. Системные настройки Java проект не меняет.

## API и Postman

### Виды работ и поиск адресов программы ремонта

`GET /api/programs/work-types` — уникальные названия `capital_repair_work_type_name`
из таблицы `program_works`, в алфавитном порядке. Параметры не нужны; NULL,
пустые строки и строки из пробелов исключаются. Названия сравниваются как хранятся в БД.
Ответ: `["Кровля", "Фасад"]`, при отсутствии данных — `[]`.

`GET /api/programs/search?workTypeName=Кровля&startDate=01.2030&endDate=12.2032`
— уникальные адреса по подстроке названия работ без учёта регистра и пересечению
периодов, включая границы. Все три параметра обязательны, даты — `ММ.гггг`.

Swagger UI: [http://localhost:8080/swagger-ui/index.html](http://localhost:8080/swagger-ui/index.html).
OpenAPI JSON: [http://localhost:8080/v3/api-docs](http://localhost:8080/v3/api-docs).
Оба эндпоинта описаны в разделе «Программы ремонта»; запросы можно выполнить из Swagger UI.

Импортировать [Postman-коллекцию](postman/RepairRadar.postman_collection.json). Переменная `baseUrl` по умолчанию `http://localhost:8080`. Установить Postman Request timeout в `0` либо достаточно большое значение: импорт синхронный, на каждом вызове читается большая иерархия. Таймаут клиента не гарантирует отмену операции на сервере. Запуск коллекции целиком заканчивается удалением всех адресов.

### Добавить адреса

`POST /api/addresses/import`, без тела:

```powershell
Invoke-RestMethod -Method Post -Uri http://localhost:8080/api/addresses/import
```

Ответ после второго импорта при достаточном числе кандидатов:

```json
{"requested":1000,"imported":1000,"total":2000,"exhausted":false}
```

`imported` — действительно добавленные строки, `total` — количество в таблице в текущей транзакции. Если осталось 37 новых адресов, добавятся 37; `exhausted=true`. Если все уже сохранены — `imported=0`, HTTP 200. `exhausted` означает, что текущий запрос не набрал 1000 новых адресов из прочитанного источника; более свежий XML может содержать новые адреса.

### Очистить таблицу

`DELETE /api/addresses`, без тела, ответ 204:

```powershell
Invoke-WebRequest -Method Delete -Uri http://localhost:8080/api/addresses -UseBasicParsing
```

Удаление выполняется одной массовой операцией. Повторный DELETE пустой таблицы также возвращает 204. После очистки ранее импортированные адреса снова доступны для импорта.

### Ошибки

Ответы ошибок — `application/problem+json` с полем `code`:

| HTTP | code | Причина |
|---|---|---|
| 422 | `GAR_SOURCE_INVALID` | Нет нужного файла, несколько совпадений, разные даты файлов |
| 422 | `GAR_XML_INVALID` | Некорректный XML, неправильный корень, запрещённый DTD |
| 409 | `ADDRESS_OPERATION_IN_PROGRESS` | В этом экземпляре приложения уже выполняется импорт или очистка |
| 404 | `ADDRESS_RESOURCE_NOT_FOUND` | Несуществующий маршрут API |
| 405 | `ADDRESS_METHOD_NOT_ALLOWED` | HTTP-метод не поддерживается маршрутом |
| 500 | `INTERNAL_ERROR` | Непредвиденная ошибка: без подробностей SQL, stacktrace и путей в ответе |
| 503 | `DATABASE_ERROR` | Ошибка операции с БД |

Дубль адреса не вызывает 409 или ошибку вставки. Реальные ошибки XML/БД не маскируются успешным ответом. Непредвиденные исключения также возвращаются как `application/problem+json` с кодом `INTERNAL_ERROR`; детали логируются на сервере и в ответ не попадают.

## XML и полный адрес

В `77` ожидается ровно один файл каждого вида одной даты (регистр расширения не важен):

- `AS_ADDR_OBJ_YYYYMMDD_*.XML`
- `AS_HOUSES_YYYYMMDD_*.XML`
- `AS_ADM_HIERARCHY_YYYYMMDD_*.XML`

StAX из Java читает XML потоком; внешние сущности и DTD запрещены. Приложение отбирает активные актуальные дома с номером, валидной активной административной цепочкой региона 77 и улицей уровня 8. Отсутствующие предки и невалидные обязательные значения исключаются со счётчиком в логе. Дубли GUID внутри XML дают одного кандидата. CSV и Python-скрипты не участвуют в работе приложения.

`full_address` включает всю административную цепочку и дом с обеими дополнительными частями номера. Например: `г. Москва, ул. Верхняя, д. 3, корп. 2`.

В исходной папке нет справочников типов. Известные подписи: HOUSETYPE=2 → `д.`, ADDTYPE=1 → `корп.`, ADDTYPE=2 → `стр.`. Другой тип сохраняется явно как `тип дома N` или `тип доп. номера N`, чтобы не выдумывать его значение; исходный код также хранится в отдельном столбце. Пустые дополнительные поля сохраняются как SQL NULL.

Память используется для активных объектов, домов и каталога подходящих кандидатов; весь XML и все элементы иерархии в память не загружаются. После чтения каталог передаётся в короткую транзакцию: блокируется запись в таблицу, исключаются сохранённые GUID, reservoir sampling выбирает до 1000 новых, `INSERT ... ON CONFLICT (house_guid) DO NOTHING` добавляет их. Ошибка SQL откатывает новые вставки целиком. Старые строки при импорте не удаляются и не обновляются. Разные экземпляры приложения сериализуют выборку/запись блокировкой PostgreSQL, SELECT остаётся доступен.

## Импорт всех улиц

`POST /api/streets/import` без тела запроса импортирует **все** актуальные активные улицы уровня 8 за один вызов, без лимита 1000. Источник — `GAR_DIRECTORY` (по умолчанию `./77`); нужны только `AS_ADDR_OBJ_YYYYMMDD_*.XML` и `AS_ADM_HIERARCHY_YYYYMMDD_*.XML` одной даты. Улицы без домов тоже загружаются. Проверяется административная цепочка региона 77 с корнем Москва; исторические записи и невалидные цепочки пропускаются.

Таблица `public.streets`:

| Поле | Значение |
|---|---|
| `street_guid` | OBJECTGUID улицы, UUID, первичный ключ |
| `street_object_id` | OBJECTID улицы, bigint |
| `name` | Тип и название из XML, например `ул. Тверская` |
| `city` | Всегда `Москва`, в том числе для улиц Троицка и Щербинки |
| `full_address` | Улица и все предки из XML, от улицы к Москве |
| `locality` | Ближайший населённый пункт с типом, например `с. Кленово`; NULL, если его нет в цепочке |
| `hierarchy_path` | Цепочка OBJECTID от Москвы до улицы, разделённых точками |

Название не уникально: разные улицы `ул. Садовая` сохраняются по собственным GUID. Для отображения и выбора используйте `full_address`, например `ул. Садовая, с. Кленово, р-н Вороново, г. Москва` и `ул. Садовая, п. ЛМС, р-н Вороново, г. Москва`. Микрорайоны и другие промежуточные уровни также сохраняются. Подписи и состав цепочки берутся из XML; отсутствующий в источнике округ не добавляется. `locality` выбирается как ближайший предок уровня 5 или 6.

Ответ: `{"inserted":0,"updated":5766,"total":5766}` (пример обогащения ранее загруженных улиц). `inserted` — добавлено, `updated` — изменено существующих строк, `total` — всего улиц в БД. Повторный импорт обновляет название и контекст по GUID, заполняет поля старых записей, а неизменившиеся строки пропускает. Строки, отсутствующие в текущем источнике, не удаляются. Вставки и обновления выполняются в одной транзакции с блокировкой таблицы; ошибка откатывает весь текущий импорт. Ошибки используют существующие коды API, включая `ADDRESS_OPERATION_IN_PROGRESS` при одновременном импорте улиц на одном экземпляре приложения.

Исходные четыре поля обязательны. Новые поля допускают NULL для совместимости со старыми записями до повторного импорта; импорт всегда заполняет `full_address` и `hierarchy_path`, а `locality` — при наличии населённого пункта. Пустые строки запрещены CHECK-ограничением.

На новой БД таблица создаётся скриптом `docker/postgres/init/001-addresses.sql`, уже подключённым к Compose. **Для существующего тома перед запуском обновлённого приложения примените миграцию** (команда использует настройки БД внутри контейнера):

```powershell
Get-Content -Raw docker/postgres/migrations/002-streets.sql | docker compose exec -T postgres sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
Get-Content -Raw docker/postgres/migrations/003-street-hierarchy.sql | docker compose exec -T postgres sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
# После миграций запустите или перезапустите обновлённое приложение, затем заполните контекст:
Invoke-RestMethod -Method Post http://localhost:8080/api/streets/import
```

Миграции добавляют таблицу и столбцы, сохраняют существующие данные и допускают повторный запуск. SQL не восстанавливает иерархию: её заполняет повторный импорт XML. Запрос импорта также добавлен в Postman-коллекцию.

## Асинхронная загрузка программ капремонта

`POST /api/repair-imports` запускает фоновую задачу через Spring `@Async`. Контроллер сразу возвращает **202 Accepted**, `Location: /api/repair-imports/{jobId}` и `{"jobId":"..."}`. `GET /api/repair-imports/{jobId}` возвращает состояние и прогресс. Второй запуск во время импорта или очистки получает **409** (`REPAIR_OPERATION_IN_PROGRESS`). Если ID не существует — **404** (`REPAIR_JOB_NOT_FOUND`).

Задача случайно выбирает до 20 разных GUID из `streets`; если улиц меньше — берёт все, если таблица пустая — завершается успешно без HTTP-запросов. Улицы и страницы обрабатываются последовательно. Перед каждым запросом выполняется новая случайная пауза 1000–3000 мс. Размер страницы — 100, нумерация начинается с 1; GUID региона всегда `0c5b2444-70a0-4932-980c-b4dc0d3f02b5`. Исходящий User-Agent: `PostmanRuntime/7.51.0` (это замена заголовка, не сокрытие IP).

Чтение продолжается до явного пустого массива `items`. Короткая страница и поле `count` не завершают обход. Отсутствующий `items`, страница без новых GUID и достижение `max-pages` считаются ошибкой, а не успешным завершением неполной загрузки. Ограничения «не более 300 результатов» нет.

В ответе статуса задачи:

| Поле | Назначение |
|---|---|
| `status` | `QUEUED`, `RUNNING`, `SUCCESS`, `PARTIAL_FAILED`, `FAILED`, `INTERRUPTED` |
| `queuedAt`, `startedAt`, `finishedAt` | Времена постановки, начала и завершения; UTC |
| `selectedStreetGuids` | Выбранные улицы |
| `successfulStreets`, `failedStreets` | Полностью вычитанные улицы / улицы с ошибкой |
| `pagesSaved`, `itemsSaved` | Зафиксированные непустые страницы / обработанные элементы; это не число уникальных вставок |
| `errorDetails` | Ошибки со streetGuid, pageIndex, HTTP-статусом и телом ошибки, если они доступны, и stack trace |

Ошибки подробно логируются и сохраняются. После ошибки одной улицы задача переходит к следующей; уже сохранённые страницы остаются. Если есть ошибки и хотя бы одна успешная улица или сохранённая страница, статус — `PARTIAL_FAILED`; если всё завершилось ошибкой без сохранённых страниц — `FAILED`. Автоматических повторов HTTP-запросов нет.

Данные нормализованы в таблицы `repair_houses`, `repair_regional_works`, `repair_kpr_works`, `repair_work_groups`. Первичный ключ — GUID соответствующего объекта; повторная загрузка обновляет значения, включая NULL. `programType` хранится в столбцах родительской записи, его GUID может быть NULL. Остальные исходные поля также допускают NULL; связь `owner_guid` работ с родителем — внутренняя обязательная связь. Денежные значения хранятся как `numeric`, известные даты — `date`, неизвестные по образцу форматы nullable-метаданных — как текст. `contracts` сохраняется в JSONB без предположений о структуре договоров. Отсутствующие в новом ответе работы не удаляются автоматически.

`repair_jobs` содержит историю задач. `repair_pages` связывает задачу, улицу и страницу, сохраняет исходный JSONB, `count` и `responseTimestamp`; таким образом не теряются неизвестные поля ответа и происхождение данных.

Каждая непустая страница сохраняется одной короткой транзакцией вместе с её прогрессом. Ошибка откатывает только эту страницу. HTTP, ожидание и весь цикл задачи не обёрнуты в транзакцию. Методы журнала используют `REQUIRES_NEW`, поэтому ошибка записи данных не откатывает запись об ошибке задачи. Вызовы идут через отдельные Spring-бины, а не через self-invocation.

Глобальная PostgreSQL advisory-блокировка предотвращает одновременные запуск/очистку даже с нескольких экземпляров приложения. На время задачи удерживается одно соединение **без открытой транзакции**; пулу нужны дополнительные соединения для коротких транзакций и чтения статуса (стандартный размер Hikari подходит). После аварийного завершения уже записанные страницы сохраняются; при следующем принятом запуске незавершённые задачи отмечаются `INTERRUPTED`. Автоматического возобновления после перезапуска нет.

`DELETE /api/repair-imports` удаляет **все полученные данные, исходные страницы и историю задач** в одной транзакции, возвращая 204. Таблицы `streets` и `addresses` сохраняются. Во время активной загрузки очистка возвращает 409.

Новая БД получает схему из `docker/postgres/init/004-repair-import.sql`. Для существующего тома перед запуском обновлённого приложения:

```powershell
Get-Content -Raw docker/postgres/migrations/004-repair-import.sql | docker compose exec -T postgres sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
$job = Invoke-RestMethod -Method Post http://localhost:8080/api/repair-imports
Invoke-RestMethod "http://localhost:8080/api/repair-imports/$($job.jobId)"
# Удаление полученных данных И истории задач:
Invoke-RestMethod -Method Delete http://localhost:8080/api/repair-imports
```

Настройки `repairradar.repair-api`: `url` (по умолчанию адрес Госуслуг из задания), `connect-timeout` (10s), `read-timeout` (60s), `max-pages` (10000). Можно переопределить стандартными Spring-переменными окружения, например `REPAIRRADAR_REPAIRAPI_URL` и `REPAIRRADAR_REPAIRAPI_READTIMEOUT`.

Интеграционные тесты используют только локальный `HttpServer` и сокращённый `src/test/resources/repair-response.json`, извлечённый из предоставленного примера. Реальное стороннее API в тестах не вызывается; задержка подменяется мок-объектом.

## Схема таблицы

| Поле CSV | PostgreSQL | Тип |
|---|---|---|
| Город | city | text NOT NULL |
| Адресная_иерархия (заменено полным адресом) | full_address | text NOT NULL |
| Улица | street | text NOT NULL |
| Дом | house_number | text NOT NULL |
| Доп_номер_1 | additional_number_1 | text |
| Тип_доп_номера_1 | additional_type_1 | integer |
| Доп_номер_2 | additional_number_2 | text |
| Тип_доп_номера_2 | additional_type_2 | integer |
| Тип_дома | house_type | integer |
| Улица_OBJECTID | street_object_id | bigint NOT NULL |
| Улица_OBJECTGUID | street_guid | uuid NOT NULL |
| Дом_OBJECTID | house_object_id | bigint NOT NULL |
| Дом_OBJECTGUID | house_guid | uuid PRIMARY KEY |

CHECK `addresses_nonempty` запрещает пустые или состоящие из пробелов city/full_address/street/house_number. Искусственного ID, дополнительных UNIQUE и внешних ключей нет. JPA проверяет схему через `ddl-auto=validate`.

## Конфигурация

`.env` автоматически читает **Compose**. Java-приложение читает переменные окружения процесса, а не `.env`.

| Переменная Java | Значение по умолчанию |
|---|---|
| DB_URL | jdbc:postgresql://localhost:5432/repairradar |
| DB_USERNAME | repairradar |
| DB_PASSWORD | repairradar_local |
| GAR_DIRECTORY | ./77 |
| SERVER_PORT | 8080 |

Compose: `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_PORT` — см. `.env.example`. Если меняете порт/учётные данные БД, согласованно задайте Java-переменные. Пример: `$env:GAR_DIRECTORY='D:\RepairRadar\77'`.

PostgreSQL хранит данные в named volume `repairradar_postgres_data`. Init SQL запускается только при первом старте на пустом томе. `docker compose down` сохраняет данные; последующий старт их не очищает. Изменение SQL не мигрирует существующий том: для изменения схемы потребуется миграция. Большие исходники `77` исключены из Git и jar.

## Проверки

```powershell
.\mvnw.cmd test     # unit-тесты
.\mvnw.cmd verify   # также интеграционные тесты с embedded PostgreSQL 18.6 (без Docker)
docker compose exec -T postgres psql -U repairradar -d repairradar -c "select count(*), count(distinct house_guid) from addresses;"
docker compose exec -T postgres psql -U repairradar -d repairradar -c "select full_address, house_guid from addresses limit 5;"
```

Интеграционные тесты поднимают отдельный embedded PostgreSQL (зонки, настоящий сервер без Docker), не рабочую Compose-базу: проверяют схему, добавление 1000→2000, дубли без перезаписи, остаток/исчерпание, rollback, конкурентные импорты, API и очистку. Для `verify` Docker не нужен.
